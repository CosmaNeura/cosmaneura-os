# Elation laboratory report reader

This inactive engineering slice supports a patient-bound report page, explicit selection of one Lab report, a fresh read, and an exact review packet. It uses only an exact `httpx.MockTransport`, an invented bearer string, and caller-supplied current-authority checks. It does not connect Elation, save a source, sign a report, or send a Chief message.

The current [List Reports](https://help.elationhealth.com/articles/rest/patient-document-api/reports/list-reports) endpoint documents patient, practice, limit and ordering parameters. It does **not** document a `report_type` query filter. The reader requests one page ordered by descending document date, validates every returned patient's/practice's identifiers, offers only exact `report_type="Lab"` candidates, and retains the number of other report types. A returned page or an empty candidate list never establishes a complete lab history or absence of testing. Continuation is validated and disclosed but never followed.

After selection, the reader re-reads the exact Patient and selected Report. Patient identity must match an existing private pin. The report must retain the selected ID, patient, practice and Lab type. A report changed since selection is retained as a fresh snapshot with an explicit change notice; it is not merged with the earlier values. Missing fields, explicit nulls and recorded blank strings remain distinct where the documented type permits them.

The [official patient-document schema](https://help.elationhealth.com/openapi/patient-document-api.yaml) describes grids containing collection/result times, accession, grid status/notes and individual results. The complete returned report JSON is preserved, including original value strings, units, reference strings, result text and notes, test identifiers, flags, statuses, dates and metadata. No result is converted to a number, normalized to different units, interpreted, deduplicated or sorted. Contradictory `is_abnormal` and `abnormal_flag` fields remain distinct. Corrected, amended, deleted and preliminary statuses are preserved as recorded; this endpoint does not establish a full correction/version chain.

The formatter creates one source of at most 5,000 Unicode codepoints and refuses the **whole** packet above that limit. Large panels will need a separately designed explicit multi-source workflow; the current reader does not silently split or shorten them. Structured grids absent, empty, and containing no rows have different notices. Attachment references and printable links remain in the original JSON, but their contents, image contents and internal notes are not fetched. The review is of returned API fields, not a complete document or chart. Embedded base64 content, unknown report/grid/result qualifiers, nonfinite or floating JSON numbers, malformed dates and unsupported types are refused rather than silently removed. The API defines clinical result values as strings; integer identifiers remain exact through int64.

[OAuth](https://help.elationhealth.com/articles/rest/overview/oauth) documents client credentials. [Token scopes](https://help.elationhealth.com/articles/rest/overview/scopes) separately document `system/reports.read` and `system/patients.read`. Reusing the existing verified-visit runtime would add reports.read to the unchanged practice/appointment/patient profile. This slice performs no OAuth exchange and has no real-credential parameter. The current documented production origin is `https://api.app.elationemr.com`; this synthetic reader permits only the existing sandbox origin. Sandbox access and live behavior remain unqualified.

For the next vertical integration, the application must derive patient/practice and authorization from its exact existing verified visit and current account, bind the destination workspace and patient link, reserve reads before provider I/O, and map public opaque candidate handles to private report IDs. It must recheck the existing visit/identity before clinical I/O and pin the exact page and fresh report snapshots in the existing EHR source custody. Client-supplied hashes are comparison inputs, never authority. Review, exact-key recovery, source withdrawal and Chief admission must reuse the existing guarded workflow. The separate integration contract in the workstream evidence gives the proposed wire and custody boundaries.
