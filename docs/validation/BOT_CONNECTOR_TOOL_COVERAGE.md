# Bot and connector tool coverage

Updated October 1, 2026. Scope: the local synthetic connector-tool profile and the existing application contracts. This is a capability map, not a statement that accounts are connected, a particular run passed, or these tools have been installed in the Mac or iPhone app engine. Use the saved run report and its exact source revision for execution evidence.

The application has four baseline roles: Chief, Scribe, Visit Prep and Follow-up. Research is an additional named role. Inbox, Scheduling, Operations and Membership / Billing are custom preset slots with specific skills and resource grants. “Office Manager” is a product description; there is no native `office_manager` role that automatically receives all administrative powers. The current connector profile uses the five named clinical/team roles, not every custom preset slot.

The authenticated first-party HTTP catalog is discovery only. Its `feature_enabled` value describes configuration; account access and operation health remain `not_checked`. The synthetic execution profile separately calls real application services against an owned database and offline provider responses. A test broker acts within the synthetic owner's scope; it does not grant production authority to an agent. Human review, approval and submission are separate from agent tools.

The profile's account reads are limited to at most 10 Google or 25 Microsoft email headers and the next seven days of at most 25 calendar summaries. They do not fetch bodies/attachments, send email or change calendars. Saving observations requires the original read key (resolved to the exact immutable hash by the server), or the exact prior read ID/hash, plus selected item IDs, current workspace revision and an idempotency key. Sign-in status is not a successful data read.

Fax tools preserve the exact selected PDF, reviewed source and recipient/account revisions. Spruce needs a separately reviewed media upload before its fax proposal. The agent-facing tools expose preparation and observation; synthetic human submission is outside their registry. SRFax, Documo and eFax delivery are accepted only under their respective receipt contracts. Spruce currently reports posting evidence and leaves final fax delivery unverified. Offline HTTP tests cannot establish a vendor's live account entitlement, current contract behavior or actual destination receipt.

The HTTP catalog now has four additional operations: `workspace.review`, `scribe.read_existing`, `scribe.share_transcript` and `visit_prep.read_brief`. Their schemas derive from actual handlers; they retain the current identity, consent, role, source-selection and revision checks. The prepared-brief schema explicitly requires `view=brief` and a bot selection instead of silently taking the route's raw-source default. `workspace.review` names the existing exact-request `/conversation/resolve` recovery route, but a separate resolve tool has not been added to that catalog.

Two concrete next connector builds fit the current local-development scope:

1. **Give Google Inbox its own selected-message source adapter.** Reuse the existing Google account custody/revocation code and private Inbox source contracts, using the Spruce adapter as a reference. Add an explicit selected-message and human-triage boundary with immutable source identity, revision/hash checks, safe attachment metadata and duplicate/out-of-order recovery in the virtual lab. Keep patient/workspace assignment explicit. If body text is needed, Gmail metadata access is insufficient: design the separate read permission and human activation flow before any live use. No such Google Inbox transport is claimed as implemented here.
2. **Expose existing scheduling preparation and receipt paths as scoped virtual tools.** Reuse the actual Scheduling preset/skill, `workspace_scheduling`, `appointment_work` and `appointment_execution`. Start with availability, exact private appointment proposal and saved status/recovery tools, leaving approval and execution outside the agent registry. Cover unavailable grants, time zones, expired slots, changed patient/resource bindings, lost replies and independently pending calendar synchronization. Add corresponding first-party discovery only for verified existing routes. This extends the current calendar-summary test into an operational scheduling workflow without inventing a new scheduling backend.
