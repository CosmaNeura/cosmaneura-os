# Bot and connector tool coverage

Updated October 2, 2026. Scope: the local synthetic connector-tool profile and the existing application contracts. This is a capability map, not a statement that accounts are connected, a particular run passed, or these tools have been installed in the Mac or iPhone app engine. Use the saved run report and its exact source revision for execution evidence.

The application has four baseline roles: Chief, Scribe, Visit Prep and Follow-up. Research is an additional named role. Inbox, Scheduling, Operations and Membership / Billing are custom preset slots with specific skills and resource grants. “Office Manager” is a product description; there is no native `office_manager` role that automatically receives all administrative powers. The current connector profile uses the five named clinical/team roles, not every custom preset slot. Google metadata intake is available to Chief/Follow-up; Scheduling uses an explicit synthetic broker and the actual reviewed Follow-up Scheduling grant.

The authenticated first-party HTTP catalog is discovery only. Its `feature_enabled` value describes configuration; account access and operation health remain `not_checked`. The synthetic execution profile separately calls real application services against an owned database and offline provider responses. A test broker acts within the synthetic owner's scope; it does not grant production authority to an agent. Human review, approval and submission are separate from agent tools.

The profile's account reads are limited to at most 10 Google or 25 Microsoft email headers and the next seven days of at most 25 calendar summaries. They do not fetch bodies/attachments, send email or change calendars. Saving observations requires the original read key (resolved to the exact immutable hash by the server), or the exact prior read ID/hash, plus selected item IDs, current workspace revision and an idempotency key. Sign-in status is not a successful data read.

Fax tools preserve the exact selected PDF, reviewed source and recipient/account revisions. Spruce needs a separately reviewed media upload before its fax proposal. The agent-facing tools expose preparation and observation; synthetic human submission is outside their registry. SRFax, Documo and eFax delivery are accepted only under their respective receipt contracts. Spruce currently reports posting evidence and leaves final fax delivery unverified. Offline HTTP tests cannot establish a vendor's live account entitlement, current contract behavior or actual destination receipt.

The HTTP catalog now has four additional operations: `workspace.review`, `scribe.read_existing`, `scribe.share_transcript` and `visit_prep.read_brief`. Their schemas derive from actual handlers; they retain the current identity, consent, role, source-selection and revision checks. The prepared-brief schema explicitly requires `view=brief` and a bot selection instead of silently taking the route's raw-source default. `workspace.review` names the existing exact-request `/conversation/resolve` recovery route, but a separate resolve tool has not been added to that catalog.

The next two connector builds are now implemented for local synthetic testing:

1. **Google metadata intake.** The dedicated Google adapter calls only the existing account's bounded mail-header read. It saves exact selected metadata as workspace evidence and a private metadata-review draft, preserving account/role/team bindings and exact retry keys. A separate scripted human reviews only the metadata, creates existing reviewed-note administrative F8 work, offers responsibility and receives explicit acceptance from a second scripted human. Chief can inspect the persisted result. Full-message clinical triage remains `needs_human`: no body or attachment access, patient matching, Gmail version/history proof, live account activation or sending is established. Google data is never relabeled as Spruce secure-message or Core preparation evidence. Observation ordering is local capture time, not provider latest-state proof.
2. **Scheduling observations and private proposals.** Existing `workspace_scheduling`, `workspace_appointments`, `appointment_work` and `appointment_execution` services run against an offline HTTP receiver. Tools retain observed slot references, exact patient/resource/Google connection bindings, workspace and team revisions, and current grant checks. The fixed New York DST fixture contains two 01:30 slots with different UTC offsets. Lost preparation and submission replies, changed bindings, expired slots and independently pending calendar synchronization have dedicated tests. Human approval/execution remains outside the tool registry. The local tool profile is book-only with a fixed invented window and a 20-item catalog; its omitted-page metadata remains visible.

First-party discovery now also describes four verified Scheduling routes: `scheduling.read_availability`, `scheduling.read_current`, `scheduling.prepare_appointment` and `scheduling.inspect_proposal`. The inspection descriptor is GET with no request body; proposal discovery requires an exact slot and explicit private sharing, and does not expose cancellation, approval or execution. Feature configuration still does not establish account or operation readiness.

The Connection directory now uses compact emoji cards and five primary states: Available, Connected, Needs setup, Needs attention and Not checked. Email and calendar successful-read evidence is separate from account sign-in. Fax preparation is separate from delivery proof, with a direct existing Fax work action gated by current preparation readiness. Practice task shortcuts open existing incoming-message/follow-up views lazily. This UI source and its synthetic desktop/phone preview are not an installed native release.

Repeatable combined case: `python -m lab.runner --cases administrative_tools --mode replay --repeat 2`, or bounded `--mode azure`. Five roles read exact evidence and share attributed drafts; separate provider/recipient actors perform human review and acceptance. The report verifies the selected Google source reaches Follow-up and Chief, exact dependencies are consumed, responsibility is accepted, message triage remains incomplete, and the appointment remains unsubmitted. A script-controlled scenario is not a fully autonomous launch workflow or clinical-quality certification.

The administrative model case offers a smaller scenario-specific tool menu per role and requests bounded Chief read batches. This reduces repeated schema overhead without changing the optional MCP registry or execution-time role checks. Calibration failures and token/latency measurements belong in the run evidence; deterministic replay is not a model-performance result.

The synthetic metadata-to-F8 human helper requires an encounter with no existing saved clinical note, except its own exact administrative-note replay. It refuses before creating a review stage when a manual, generated or Core-backed note already exists. The case supplies typed Scribe draft artifacts; it does not overwrite a clinical note. Supporting metadata handoffs alongside an existing clinical note needs a separately reviewed source contract.
