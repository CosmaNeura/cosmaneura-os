# Athena recorded medication entries

This is an inactive, synthetic-only reader and exact review formatter. It does not establish a live connection, install OAuth, save a source, grant access, submit a prescription, or determine current medication use. The subsequent application workflow must select an independently authorized medication patient, revalidate the grant and identity, obtain fresh human review, and use existing source custody/recovery and Chief admission checks.

## Verified provider contract

Official public documentation was captured on October 26, 2026 from [Athena medication API reference](https://docs.athenahealth.com/api/api-ref/medication), content entry `https://docs.athenahealth.com/v1/api/entries/exploreDocs?urlAlias=%2Fapi-ref%2Fmedication&include=5`. The captured entry SHA-256 is `28bc85cd0420b029a86bcc8200ae1d32cd9c98c88c3468fe5acc6b2597ba2ee5`; the extracted GET contract SHA-256 is `5d5194c2a377a608c3e0d0dc627bc2724eaf49d73ab049e2c4261fbd54f0a849`. Evidence is under the workstream's `evidence/athena-clinical-read/`.

The bounded query is `GET /v1/{practiceid}/chart/{patientid}/medications?departmentid={authorized_department}&medicationtype=ACTIVE&showpend=true&showndc=true&showrxnorm=true`. A fresh `GET /v1/{practiceid}/patients/{patientid}?departmentid={authorized_department}` must first match the server-pinned Patient identity. Patient registration/current department is identity data; it does not authorize a chart department. Account, practice, chart department, patient, owner, Box, workspace/current patient link, connection generation and medication authorization are independent pins. Allergy and scheduling permissions cannot substitute for medication authorization.

The preview origin is `https://api.preview.platform.athenahealth.com`; production is `https://api.platform.athenahealth.com`. These documented origins do not establish sandbox access or product authorization. Only an exact `httpx.MockTransport` is accepted, with an invented token. The reader does not send `PATIENTFACINGCALL` (documented to store data) or `THIRDPARTYUSERNAME`. It follows no redirect, retries no request and makes no download/write/renewal call.

The provider offers ACTIVE, HISTORICAL and DENIED query values; omission has no qualified default. This slice explicitly requests ACTIVE with pending entries. It does not claim complete medication history or current use. PEND entries represent approved future orders not yet submitted. `isdiscontinued` concerns whether the medication can be ordered, rather than establishing that the patient stopped it. `lastdownloadeddate` is an attempted history-download time, not proof of success. Download consent/denial fields, flags, notes, dates and status strings remain exact. No meaning is invented for `issafetorenew`.

## Exact data representation

`medications` is an array of arrays. Group meaning is not documented, so order, empty groups and repeated entry IDs are preserved. An absent entry ID/name remains absent; blank stays blank. An empty response and `nomedicationsreported` absent/false/true remain distinct. Contradictory returned entries and an explicit no-medications statement are both retained. Unknown documented-object fields or malformed known values refuse the complete packet. Only `events[].userdisplayname` is documented as nullable; `structuredsig` is an opaque object whose nested values may include null.

A medication-only `RecordedNumber` keeps each exact JSON number token, including `0.50`, `1e-7`, `-0` and signed-int64 boundary values. No float, exponent expansion or numeric normalization occurs. Known integer fields (`medicationid`, `encounterid`, `refillsallowed`) require integer-token grammar and signed-int64 range. `quantity` and opaque structured-sig numbers retain raw tokens. Public clinical content must remain canonical JSON strings; outer counts alone may use safe integer fields.

Canonical JSON sorts keys by Unicode scalar/codepoint order, preserves arrays, emits Python-compatible ASCII JSON string escaping, and retains exact numeric spelling. Duplicate decoded keys, invalid UTF-8, NUL and lone surrogates refuse. Valid escaped controls other than NUL, including tabs/CR/LF, survive. Data objects named `kind`, `raw`, `token` or `__proto__` cannot impersonate the private number class. SQL must traverse `json` tokens without a clinical `jsonb`/float cast; JavaScript must use an unforgeable numeric representation and explicit codepoint sorting rather than default UTF-16 sort.

Limits are 65,536 raw UTF-8 bytes; depth16 with root depth0; 4,096 JSON values; 64 object members; 256 generic array elements; 128-codepoint keys; 4,096-codepoint clinical strings; 128-character number tokens; 25 groups and 25 total entries; 100 events/NDC/RxNorm entries per medication. Entry IDs are at most300 codepoints. The existing Patient identity/strict scope label rules are unchanged. Excessive parser nesting becomes a supported refusal.

## Review and integration boundary

`AthenaMedicationReader.read()` returns `AthenaMedicationObservation`: independent scope, exact Patient identity, aware observation time, grouped private records, complete `section_json`, two raw response hashes and a medication-specific observation commitment. Query flags are explicit and fixed in both scope and observation. `prepare_medication_review()` checks exact scope/source/identity pins, re-derives the projection, preserves the entire original section in the canonical source and rechecks authority before release.

The complete source must fit5,000 Unicode codepoints. It is refused as a whole if oversized; no record, qualifier, instruction or field is silently omitted or truncated. Patient/registration IDs stay private, while the exact medication packet remains reviewable. Numeric spelling and clinical string values are preserved, not irrelevant original JSON whitespace/key order. Recorded dates are not parsed into inferred precision/timezones.

Hash domains are `athena-medication-patient-scope.v1`, `athena-medication-observation.v1` and `athena-medication-review-snapshot.v1`. Existing allergy domains and behavior remain untouched. The next vertical uses explicit `provider=athena`, `protocol=core`, `clinical_scope=medications`, independent medication grants and `core_patients` → `core_medications` → review → existing saved-source/Chief workflow. Reader/formatter unit qualification alone is not signed API/SQL/browser/native or live-vendor qualification.
